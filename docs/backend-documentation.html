۱. معرفی کلی و پشته فناوری

DiGiFACE یک مارکت‌پلیس تخصصی محصولات آرایشی و بهداشتی است که سه نقش اصلی سمت عرضه/تقاضا را به هم وصل می‌کند: مشتری، فروشگاه و پیک (تحویل‌دهنده)، به‌علاوه یک پنل ادمین برای نظارت و یک لایه هوش مصنوعی برای تصمیم‌گیری‌های خودکار (تأیید محصول، دسته‌بندی تیکت، تخمین اندازه بسته و پردازش سفارشات خارج‌شهر).

لایهفناوری
فریم‌ورکNext.js 14 (App Router)
زبانTypeScript
ORM / دیتابیسPrisma 5 روی PostgreSQL (به‌صورت provider در schema)؛ توضیحات پروژه اشاره به MySQL پارس‌پک دارد — به بخش ۷ مراجعه شود
احراز هویتJWT دست‌ساز با کتابخانه jose + کوکی httpOnly + هش رمز عبور با bcryptjs
استایلTailwind CSS + فونت وزیرمتن (فارسی) و Cormorant Garamond
UI کمکیlucide-react, sonner (toast), class-variance-authority, tailwind-merge

۲. معماری کلی پروژه

پروژه به‌صورت یک اپلیکیشن Full-stack یکپارچه در Next.js نوشته شده؛ یعنی هم فرانت‌اند (صفحات React) و هم بک‌اند (API Routes زیر src/app/api) در یک ریپازیتوری هستند. ساختار پوشه‌بندی به‌صورت Route Groups سازمان‌دهی شده است:

src/app/
├── (mainsite)/        صفحات عمومی: لندینگ، فروشگاه‌ها، سبد خرید، احراز هویت
├── (panels)/           پنل‌های نقش‌محور: account, shop-panel, pick-app, admin
├── api/                API Routes (سمت سرور)
├── layout.tsx          Layout ریشه (فونت + RTL)
└── middleware.ts       محافظت مسیر بر اساس نقش کاربر

۲.۱ جریان یک درخواست

هر درخواست ورودی به مسیرهای /account/* یا /admin/* ابتدا از middleware.ts عبور می‌کند. میان‌افزار توکن Session را از کوکی می‌خواند، با verifySessionTokenEdge (نسخه سازگار با Edge Runtime از jose) اعتبارسنجی می‌کند و بر اساس نقش کاربر (role) تصمیم می‌گیرد که اجازه عبور بدهد، به صفحه لاگین ریدایرکت کند یا کاربر غیرمجاز را به مسیر مناسب نقش خودش بفرستد.

درخواست‌های API از طریق fetch در سمت کلاینت (عمدتاً از طریق تابع کمکی apiFetch) ارسال می‌شوند، هندلر Route در src/app/api/.../route.ts پاسخ می‌دهد، و منطق دیتابیس از طریق Prisma Client مشترک (src/lib/prisma.ts) اجرا می‌شود.

۳. تحلیل کامل دیتابیس (Prisma Schema)

دیتابیس شامل ۷ Enum و ۲۹ مدل است که در ۱۳ حوزهٔ کسب‌وکار (Domain) سازمان‌دهی شده‌اند. در ادامه هر حوزه به‌همراه هدف، فیلدهای کلیدی و روابط آن شرح داده شده است.

۳.۲ کاربران و احراز هویت

User

هستهٔ مرکزی کل سیستم. فیلدهای کلیدی: phone (یکتا، شناسهٔ اصلی ورود)، phoneVerified، username (یکتا)، passwordHash، role، score و tier (سیستم امتیازدهی)، negativeBalance (بدهی کاربر در صورت عودت سفارش با موجودی ناکافی کیف پول). هر کاربر بسته به نقش می‌تواند دقیقاً یکی از روابط اختیاری shop، pick یا adminProfile را داشته باشد (الگوی Table-per-role روی یک User مرکزی).

OtpCode

کدهای یک‌بارمصرف پیامکی برای تأیید موبایل؛ هر رکورد phone, code, expiresAt, used دارد. با هر درخواست کد جدید، کدهای قبلی همان شماره حذف می‌شوند.

Address

آدرس‌های چندگانهٔ هر کاربر با برچسب (خانه/محل کار/سایر)، مختصات جغرافیایی (lat/lng) برای محاسبهٔ فاصله و آدرس پیش‌فرض.

ScoreHistory

تاریخچهٔ تغییرات امتیاز کاربر (points می‌تواند منفی باشد) با دلیل (خرید، ثبت‌نظر به‌موقع، معرفی دوست، تخلف و...) — مبنای محاسبهٔ Tier کاربر.

۳.۳ شهر و زیرساخت حمل‌ونقل (مدیریت ادمین)

City

فهرست شهرهای فعال پلتفرم؛ به فروشگاه، پیک، سرویس‌های حمل و سفارش‌ها متصل است.

CarrierService

سرویس‌های حمل بین‌شهری (پست ایران، الوپیک، تیپاکس و...) که ادمین به‌ازای هر شهر تعریف می‌کند؛ شامل زمان تخمینی تحویل و آدرس دفتر برای هماهنگی پیک منتخب.

BoxFilter

فیلترهای تعریف‌شده توسط ادمین برای باکس‌ها به تفکیک شهر (اندازه، مبدأ برند، تعداد قلم و...).

۳.۴ فروشگاه، محصول و باکس

Shop

پروفایل فروشگاه شامل مدارک (licenseFileUrl)، موقعیت جغرافیایی، وضعیت بررسی (ShopStatus) و دو نرخ کمیسیون جداگانه: productCommission (پیش‌فرض ۷٪) برای فروش محصول تکی و boxCommission (پیش‌فرض ۲۰٪) برای باکس. تغییر کمیسیون از طریق pendingCommissionChange (JSON) در انتظار تأیید فروشگاه می‌ماند — یعنی پلتفرم نمی‌تواند یک‌طرفه کمیسیون را تغییر دهد.

Product

محصول متعلق به یک فروشگاه با گردش تأیید هوش مصنوعی (status: PENDING_AI → APPROVED/REJECTED_AI). اگر فروشنده روی محصولِ رد‌شده اصرار کند، forceEditRequested فعال شده و پرونده به ادمین ارجاع می‌شود (PENDING_ADMIN). ویرایش‌های بعدی در pendingEdit (JSON) صف می‌شوند و هر ویرایش جدید، ویرایش قبلی صف را جایگزین می‌کند. isInStock=false یعنی محصول به‌صورت خودکار از نتایج محو می‌شود بدون حذف رکورد.

Box / BoxItem / BoxFilter

باکس، بستهٔ چند-محصولی تخفیف‌دار یک فروشگاه است (originalPrice در برابر discountedPrice). هر BoxItem یا به یک Product موجود اشاره می‌کند یا یک آیتم اختصاصی باکس است (customName/customPrice) که در این حالت نیاز به تأیید ادمین دارد (needsAdminApproval). فیلد isInterShopEnabled امکان می‌دهد باکس یک فروشگاه، در ویترین فروشگاه‌های دیگر هم قابل سفارش باشد (باکس بین‌فروشگاهی).

۳.۵ کمپین‌ها

Campaign / ShopCampaign

Campaign یک تخفیف زمان‌دار سراسری با commissionPercent ویژهٔ خودش است. فروشگاه‌ها باید صریحاً بپیوندند (ShopCampaign.accepted) و می‌توانند انتخاب کنند که کمپین روی همهٔ محصولاتشان اعمال شود (appliesToAll) یا فقط زیرمجموعه‌ای انتخابی (selectedProductIds).

۳.۶ پیک (تحویل‌دهنده)

Pick

پروفایل پیک با مدارک هویتی/خودرو، وضعیت بررسی مشترک با فروشگاه (ShopStatus)، و نرخ کمیسیون پلتفرم از پیک (پیش‌فرض ۱۶٪) که تغییرش نیازمند تأیید دومرحله‌ای پیک است (commissionApproved). دو پرچم انتخاب ویژه دارد: isSelectedForIntercity (پیک منتخب برای هماهنگی سفارش‌های خارج‌شهر) و isSelectedForChecks (برای کاربران چکی فاز ۲).

۳.۷ سفارش — قلب سیستم

مدل Order پیچیده‌ترین بخش دیتابیس است و کل چرخهٔ عمر سفارش را به‌صورت یک ماشین‌حالت با ۱۵ وضعیت مدل می‌کند:

CART_SAVED → PENDING_SHOP → CONFIRMED → PICK_SEARCHING → PICK_ASSIGNED
→ PICK_PICKED_UP → OUT_FOR_DELIVERY → DELIVERED → COMPLETED

مسیرهای انحرافی:
CANCELLED_BY_USER   (قبل از تأیید فروشگاه)
CANCELLED_BY_SHOP   (رد توسط فروشگاه)
PARTIALLY_FULFILLED (برخی اقلام حذف شد)
RETURNED            (عودت توسط پیک)
ESCALATED_ADMIN     (تایمر پاسخ‌گویی گذشت)
INTERCITY_PROCESSING(در حال پردازش سفارش خارج‌شهر توسط AI/ادمین)

فیلدهای زمان‌بندی روی خود مدل Order نشان می‌دهند چند مهلت (SLA) به‌صورت خودکار روی سفارش اعمال می‌شود:

  • تحویل پیک: ۳ ساعت پس از تحویل‌گرفتن از فروشگاه (pickDeliveredAt)
  • ارزیابی مشتری: ۷ ساعت برای سفارش همشهری (با توقف بازهٔ ۷ شب تا ۸ صبح) یا ۹۶ ساعت برای خارج‌شهر (reviewDeadline)
  • پشتیبانی سفارش: تا ۱ هفته پس از ثبت قابل پیگیری است (supportDeadline)

فیلد pickContactMode انتخاب می‌کند ارتباط مشتری و پیک از طریق پلتفرم (secure) باشد یا مستقیم. آیتم‌های سفارش (OrderItem) هرکدام به یک فروشگاه وصل‌اند؛ در سناریوی باکس بین‌فروشگاهی، isInterShopFulfillment و fulfillingShopId نشان می‌دهند کالا واقعاً توسط فروشگاه دیگری تأمین شده. OrderItemProduct نیز محصولات داخل هر باکس سفارش‌داده‌شده را ردیابی می‌کند.

۳.۸ ارسال خارج‌شهر

Shipment

برای سفارش‌های INTERCITY. هزینه از فرمول هزینهٔ پست محلی × ۱.۳ + هزینهٔ پلتفرم بین‌شهری محاسبه می‌شود (localPostCost, platformFee, totalCost). processedByAi نشان می‌دهد آیا انتخاب مسیر/سرویس حمل توسط هوش مصنوعی خودکار انجام شده یا نه.

۳.۹ ارزیابی و تخلفات

Review

ارزیابی مشتری با سه حالت (GREAT/NORMAL/REPORT). اگر گزارش تخلف باشد، ادمین باید ظرف ۲۴ ساعت بررسی کند (adminReviewed). اگر سیستم نتواند خودکار جمع‌بندی کند، تماس کارشناس با ضبط مکالمه ثبت می‌شود (callRecordingUrl, resolvedByCall).

ViolationReport

گزارش تخلف پیک یا مشتری، مستقل از Review، با فیلد resolution برای نتیجهٔ بررسی ادمین.

۳.۱۰ کیف پول و تراکنش‌های مالی

Wallet / Transaction / WithdrawalRequest

هر کیف پول دقیقاً به یکی از سه نوع مالک (مشتری/فروشگاه/پیک) متصل است. برای پیک، grossEarnings درآمد ناخالص را جدا از balance (موجودی خالص قابل برداشت) نگه می‌دارد. تغییر اطلاعات بانکی برای تسویه از مسیر تأیید دومرحله‌ای عبور می‌کند (pendingBankChange). هر Transaction یک type از هشت نوع ممکن دارد و amount می‌تواند منفی باشد (مثلاً برای برداشت یا کسر کمیسیون). درخواست برداشت وجه (WithdrawalRequest) گردش وضعیت ساده‌ای دارد: pending → approved/rejected → paid.

۳.۱۱ تیکت پشتیبانی

Ticket / TicketMessage

هر تیکت یک عنوان تولیدشده توسط AI (aiTitle) و یک دسته از ۸ دستهٔ ممکن دارد. پیام‌های داخل تیکت مشخص می‌کنند فرستنده کدام نقش بوده (senderRole) — بنابراین گفت‌وگوی چندنقشی (مشتری/فروشگاه/پیک/ادمین) در یک تیکت ممکن است.

۳.۱۲ ادمین و ثبت رخدادها

AdminProfile / AuditLog

دسترسی‌های هر ادمین به‌صورت JSON آزاد تعریف می‌شود (permissions) که انعطاف بالایی برای تعریف نقش‌های سفارشی می‌دهد؛ isSuperAdmin دسترسی کامل بدون محدودیت. تمام اقدامات حساس ادمین (تأیید فروشگاه، رد پیک، ویرایش کمیسیون و...) در AuditLog با جزئیات JSON ثبت می‌شود — یک الزام امنیتی/حسابرسی مهم.

Notification

اعلان درون‌برنامه‌ای یا پیامکی به کاربر، معمولاً وابسته به یک سفارش خاص.

۳.۱۳ کلان‌داده و هوش مصنوعی

BehaviorLog

لاگ رفتار کاربران (جست‌وجو، مشاهدهٔ محصول، افزودن به سبد و...) حتی برای بازدیدکنندگان مهمان (userId اختیاری، sessionId اجباری) — پایهٔ تحلیل رفتاری و شخصی‌سازی.

AiLog

ثبت هر تصمیم هوش مصنوعی (بررسی محصول، دسته‌بندی تیکت، تخمین اندازهٔ بسته، پردازش ارسال بین‌شهری، فشرده‌سازی فایل) به‌همراه ورودی/خروجی و نتیجهٔ نهایی (decision) — برای رهگیری و اشکال‌زدایی تصمیمات خودکار.
جمع‌بندی روابط کلیدی: User مرکز گراف است. از آن به Shop، Pick و AdminProfile شاخه می‌زند. Order سه ضلع اصلی (User مشتری، Shop از طریق OrderItem، و Pick) را به‌هم وصل می‌کند و خودش منشأ Transaction، Review، Shipment و Notification است. الگوی JSON برای فیلدهای "در انتظار تأیید" (pendingEdit, pendingCommissionChange, pendingBankChange) در چند مدل تکرار شده — یک تصمیم طراحی آگاهانه برای گردش‌کار "تغییر پیشنهادی + تأیید طرف مقابل".

۴. سیستم احراز هویت (Auth)

سیستم احراز هویت به‌صورت دست‌ساز (بدون NextAuth) با JWT پیاده شده و دو مسیر ثبت‌نام دارد: ثبت‌نام با موبایل + OTP و ورود با یوزرنیم/موبایل + رمز عبور.

۴.۱ جریان ثبت‌نام (۳ مرحله)

  1. ارسال کد (send-otp): شمارهٔ موبایل نرمال‌سازی می‌شود؛ اگر کاربری با همان شماره از قبل phoneVerified=true دارد، خطای ۴۰۹ برمی‌گردد (هدایت به صفحهٔ ورود). در غیر این صورت یک کد OTP ساخته و رکوردهای قبلی همان شماره حذف می‌شوند.
  2. تأیید کد (verify-otp): کد ۶ رقمی در برابر آخرین رکورد معتبر و استفاده‌نشده بررسی می‌شود؛ در صورت صحت، یک توکن تأیید کوتاه‌عمر (۱۵ دقیقه، JWT با purpose: register) صادر می‌شود.
  3. تکمیل پروفایل (register): با ارائهٔ توکن تأیید + نام + یوزرنیم + رمز عبور، رکورد کاربر با upsert ساخته/به‌روزرسانی می‌شود، رمز با bcrypt هش می‌شود و بلافاصله یک Session Token صادر و در کوکی httpOnly ذخیره می‌شود (یعنی کاربر بعد از ثبت‌نام خودکار وارد می‌شود).

۴.۲ جریان ورود (login)

ورودی identifier می‌تواند شماره موبایل یا یوزرنیم باشد؛ سیستم به‌صورت خودکار تشخیص می‌دهد (اگر شکل موبایل معتبر نبود، به‌عنوان یوزرنیم نرمال می‌شود). رمز عبور با bcrypt.compare بررسی، وضعیت isActive کاربر چک، و در صورت موفقیت Session Token صادر می‌شود.

۵. نقشهٔ کامل API

در زمان بررسی، تنها API Routeهای زیر بین Backend واقعی و Prisma پیاده‌سازی شده‌اند. سایر بخش‌های پروژه (سفارش، محصول، فروشگاه، کیف پول، تیکت، ادمین) در فرانت‌اند با دادهٔ نمایشی ثابت (mock/demo) پیاده شده‌اند و هنوز به دیتابیس واقعی متصل نیستند — هرچند مدل‌های دیتابیس مربوطه از قبل در schema آماده‌اند.

۶. منطق‌های کسب‌وکار طراحی‌شده (از طریق تحلیل Schema)

حتی بدون کد API، بخش زیادی از منطق تجاری محصول از طریق طراحی مدل‌های دیتابیس و کامنت‌های فارسی داخل schema قابل استخراج است:

۶.۱ کمیسیون‌های چندلایه

  • کمیسیون فروش محصول تکی: ۷٪ پیش‌فرض
  • کمیسیون فروش باکس: ۲۰٪ پیش‌فرض
  • کمیسیون پلتفرم از پیک: ۱۶٪ پیش‌فرض
  • هر تغییر در این نرخ‌ها نیازمند تأیید طرف مقابل (فروشگاه/پیک) است — پلتفرم نمی‌تواند به‌صورت یک‌طرفه تغییر دهد.

۶.۲ جریمهٔ عودت سفارش

وقتی پیک سفارشی را عودت می‌دهد (Order.isReturned)، طبق نوع تراکنش PICK_FEE_PENALTY، ۱.۵ برابر هزینهٔ پیک از کیف پول مشتری کسر و به پیک پرداخت می‌شود.

۶.۶ باکس بین‌فروشگاهی

وقتی Box.isInterShopEnabled=true باشد، آن باکس می‌تواند از ویترین فروشگاه‌های دیگر هم سفارش داده شود؛ در این حالت OrderItem.isInterShopFulfillment=true و fulfillingShopId فروشگاه واقعیِ تأمین‌کننده را مشخص می‌کند (مالک باکس و تأمین‌کنندهٔ واقعی می‌توانند متفاوت باشند).

۶.۷ سیستم امتیاز و سطح‌بندی کاربر

هر رویداد مثبت/منفی (خرید، ثبت‌نظر به‌موقع، معرفی، تخلف) یک رکورد در ScoreHistory ایجاد می‌کند و مجموع امتیاز، tier کاربر را در چهار سطح Bronze/Silver/Gold/Platinum تعیین می‌کند.

۷. امنیت، ریسک‌ها و نکات فنی

موضوعوضعیت / ریسک

۸. راهنمای دیپلوی (خلاصه)

بر اساس سند داخلی پروژه، استقرار روی هاست اشتراکی پارس‌پک با پشتیبانی Node.js به این ترتیب انجام می‌شود:

  1. ساخت دیتابیس MySQL و کاربر آن در cPanel، تنظیم DATABASE_URL در فایل .env
  2. اجرای npx prisma generate و npx prisma migrate deploy
  3. ساخت پروژه با npm run build
  4. فعال‌سازی Node.js App در cPanel (نسخهٔ ۱۸ به بالا) با فایل استارتاپ سفارشی server.js که سرور HTTP سفارشی Next.js را اجرا می‌کند
  5. آپلود فایل‌ها (به‌جز node_modules و .next)، اجرای npm install روی سرور و ری‌استارت اپلیکیشن

۹. جمع‌بندی و پیشنهادات بعدی

  • اولویت اول: پیاده‌سازی API واقعی برای سفارش‌ها، چون این مدل قلب کل سیستم است و همهٔ سه نقش (مشتری/فروشگاه/پیک) و لایهٔ مالی به آن وابسته‌اند.
  • رفع ناسازگاری provider دیتابیس (MySQL در برابر PostgreSQL) پیش از هرگونه Migration روی محیط Production.
  • پیاده‌سازی ارسال واقعی پیامک OTP و حذف افشای کد تست از پاسخ API.
  • افزودن Rate limiting روی Endpointهای احراز هویت.
  • اتصال تدریجی پنل‌های فروشگاه، پیک و ادمین به API واقعی، به‌ترتیب اولویت کسب‌وکار.
  • پیاده‌سازی لایهٔ هوش مصنوعی که در schema پیش‌بینی شده (AiLog, aiCheckNote, processedByAi, aiTitle) اما هنوز در کد سرویس واقعی ندارد.
